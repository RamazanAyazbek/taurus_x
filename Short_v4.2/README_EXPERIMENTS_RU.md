# TAURUS SHORT — 3 независимых эксперимента (research-only)

Исходный `config.py`, `main.py`, `backtester.py`, `signal_logic.py`, `exit_logic.py`, `log_parser.py` **не менялись**. Исходный запуск `python main.py` работает как прежде. Единственное изменение в существующем файле `market_data.py` — добавлено поле `open` в загружаемые 1m свечи Binance (это не влияет на старый `find_exit`). Новые компоненты запускаются **только локально**. Ни один ордер на Binance они не создают.

## Как запустить в Windows

1. Распаковать архив.
2. Перейти в папку `Short_v4.1`.
3. В консоли выполнить `python -m pip install -r requirements.txt`.
4. Запустить `run_experiments.bat` двойным кликом или выполнить `python run_experiments.py` в консоли.
5. После загрузки Binance Futures 1m открыть `results/experiments/comparison.csv` и файлы сценариев.

Для проверки работы **без Binance**: `python self_test.py`. Для проверки имеющихся 15 результатов без Binance: `python offline_historical_audit.py` (приближённая оценка *только двух риск-режимов*, НЕ новый backtest и НЕ результаты третьего варианта).

Нужен рабочий интернет и доступ к `https://fapi.binance.com/fapi/v1/klines` для полного запуска. Загрузка в первый раз может включать десятки запросов. Свечи всех сценариев кешируются в `data/binance_1m_cache/`, поэтому повторные тесты используют те же данные. Если последний день был загружен неполностью, при следующем запуске обновляется.

## Что сравнивается

| CSV | Смысл | Входы пропускаются? |
|---|---|---|
| `baseline.csv` | Исходный v7.3, неизменённый вход Collector и TP 1.5% / SL 0.7% | По исходным правилам |
| `support.csv` | Если рядом **объявленная в Collector** поддержка S1 — гипотетический объём ×0.5 | Нет |
| `taker.csv` | Рост Taker Buy за 20 минут >=7 процентных пунктов — объём ×0.5 | Нет |
| `preentry.csv` | **Все** входы пересчитываются по 1m **OPEN** ровно через 3 минуты после подтверждения. Если цена упала >=0.20% — объём ×0.5 | Нет по правилу (но без нужной свечи неизвестно) |
| `combined.csv` | Все три вместе; условный объём = произведение коэффициентов, минимум ×0.25 | Нет |

Пороговые параметры: `experiment_config.py`. Меняйте **только один порог за раз** и сравнивайте на одном периоде. Эти значения — исследовательские стартовые настройки, НЕ доказанная оптимизация.

### A — расстояние до S1

Ищем **последнюю известную** отметку `S1[нижняяk-верхняяk]` в Collector за 60 минут **до подтверждения включительно**. Если цена подтверждения находится внутри S1 или не более чем на 0.35% **выше верхней границы**, риск условно уменьшается вдвое. Если цена уже **ниже нижней границы** зоны, такую зону не считаем поддержкой. Если S1 неизвестна (`NONE`), **не считаем, что поддержки нет**: признак остаётся неизвестным, размер исходный. Другие настоящие уровни, которых в логе нет, не додумываются. Новых свечей для уровней не используем, чтобы избежать просмотра вперёд.

В отчёте: `support_low/high`, `support_observed_at`, `support_distance_pct`, `support_near`.

### B — ускорение Taker Buy

Берём Taker Buy на подтверждении минус запись примерно 20 минут назад (запись должна быть не старше точки отсчёта более чем на 10 минут). Если предыдущая запись отсутствует или слишком старая, признаки пустые, без штрафа. **7.0 pp** означает, например, `34.7% → 42.4%` (+7.7 процентных пункта), а не изменение на 7% относительно первоначального значения.

В отчёте: `taker_buy_lookback`, `taker_buy_delta_pp`, `taker_buy_rising_fast`.

### C — проверка и пересчёт цены входа

Симулятор в этом сценарии предполагает, что решение об открытии исполняется не на момент записи Collector, а на открытии **минутной** свечи Binance Futures **через 3 минуты**. Например, подтверждение 19:30 → гипотетический MARKET в 19:33:00 по 1m OPEN. Это **приближение**, не фактическая котировка в 19:33:05 и не реальное проскальзывание. TP/SL считаются от новой цены, временной лимит от нового входа. Сам расчет выхода (`exit_logic.find_exit`) не изменён: он по-прежнему **игнорирует первую 1m свечу**, что является известным ограничением и позднее должно быть исправлено отдельно.

Если цена упала >=0.20% от подтверждения до гипотетического входа, объём ×0.5. При отсутствии строго требуемой минуты **не используем соседнюю свечу**; учитываем в `preentry_candle_missing_excluded`. Тест C не может быть оценён через один только Collector Log.

В отчёте: `confirmation_time`, `confirmation_price`, `entry_time`, `entry_price`, `preentry_move_pct`, `preentry_fell_fast`.

## Интерпретация результатов

- `net_pnl_pct` — результат сделки на номинал **без учёта** уменьшения условного объёма.
- `size_multiplier` — теоретический коэффициент размера позиции относительно одинакового номинала исходной версии.
- `weighted_net_pnl_pct = net_pnl_pct × size_multiplier`; `sum_net_pct_weighted` — **сумма условных вкладов**, не доходность депозита и не доходность на маржу с 25x, и не исполнимые реальные объёмы BTC. При маленьком размере базовой сделки округление лота Binance может не позволить реализовать х0.5/х0.25.
- `winrate_tp_over_tp_sl_pct` не учитывает Timeout (как исходный проект). Режимы A и B меняют размер, а не исход сделки — их TP/SL/Win Rate совпадут с baseline при той же истории.
- `unresolved_exits_excluded` = позиций, которым в 1m истории не найден TP/SL/Timeout. **По просьбе пользователя статус таких позиций пока не исправляем**. Они по-прежнему не попадают в итоговые сделки; интерпретируйте последние даты осторожно.
- `baseline_signals_missing` и `additional_signals_vs_baseline` выявляют расхождения состава завершённых сделок по времени сигнала (важно для C из-за иных сроков закрытия и State Lock). Не смешивайте изменение состава с изменением исхода при том же сигнале.

Исходная модель комиссии TP — 0.07% (taker+maker), SL — 0.10%, TIMEOUT — 0.10%; фандинг, проскальзывание, лотность и неполнота первого минутного бара здесь **не решены**. Нельзя считать результаты точным воспроизведением Production.
